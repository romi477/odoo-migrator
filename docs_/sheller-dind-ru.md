# Sheller: контейнеризованный режим демона (DooD)

> **Статус: реализовано (2026-09-20).** Этот файл — исходное ТЗ, оставлен
> как история решений. Актуальный рантайм-контракт, против которого пишет
> мигратор, — `odoo-sheller/docs/container.md`. Где расходится — прав
> `container.md`. Главные отличия от текста ниже: путь состояния внутри
> контейнера `/data/.odoo-sheller` (не `/root/...`); `ODOO_SHELLER_UID`/
> `_GID` передаются явно, а не только выводятся из владельца директории;
> имя контейнера свободное, поиск по label
> `io.github.romi477.odoo-sheller`; rootless Docker поддержан.

Спецификация на разработку в проект `odoo-sheller`. Цель — третий
уровень резолвинга демона со стороны Odoo Migrator (см.
`description-ru.md` / `sheller-ru.md`): если на хосте нет ни живого
демона на 8765, ни установленного бинаря — мигратор должен уметь сам
поднять демон как Docker-контейнер.

Термин **DooD** (Docker-outside-of-Docker), не DinD: демон-контейнер не
поднимает свой собственный Docker daemon внутри себя, он получает
доступ к **host'овому** `docker.sock` и говорит с тем же Docker Engine,
что и остальные контейнеры на машине. Демон уже устроен именно так —
меняется только то, откуда он сам запущен.

## Итог аудита текущего кода (2026-09-20)

Проверено по `docs/architecture.md`, `README.md`, `odoo_sheller/transport.py`.

- Демон — обычный процесс, который сам делает `docker exec -i
  <container> ...` как pipe в `odoo-bin shell`. Ничего не
  устанавливается и не копируется в целевой контейнер — bootstrap
  течёт через stdin heredoc самого exec-канала.
- Список баз данных читается **пробным процессом внутри целевого
  контейнера** (`psycopg2`, который там уже есть), не самим демоном по
  сети. **Демону не нужен сетевой доступ до Postgres целевого проекта
  и не нужно быть в одной docker network с ним** — только доступ до
  Docker socket, чтобы делать `exec`/`ps`.
- `docker_bin()` в `transport.py` уже читает путь к `docker` CLI через
  `ODOO_SHELLER_DOCKER`, с фолбэком на просто `"docker"` в `PATH`.
  Комментарий в коде explicitly объясняет, что спец-путь нужен только
  для **macOS GUI-приложения** (у него минимальный PATH, Docker
  Desktop туда не попадает) — "a terminal session is unchanged". То
  есть headless-демон, запущенный не из GUI-обёртки (в терминале или в
  контейнере), уже сейчас находит `docker` через обычный `PATH` без
  доработок.
- Поиск по коду (`odoo_sheller/`) на macOS-специфичные вызовы
  (`sys.platform`, `darwin`, keychain, `~/Library`) — **пусто**. Не
  найдено ни одного платформенного условия внутри демона. Пометка
  "OS: macOS (daemon is not containerized)" в README — похоже,
  задокументированный и протестированный периметр, а не жёсткая
  архитектурная зависимость. Тестировать/подтверждать всё равно нужно,
  но переписывать логику, скорее всего, не придётся.
- Пакетно демон уже отделён от desktop-приложения: `packaging/
  odoo-sheller.spec` фризит демон отдельно от `odoo-sheller-app/`.

Вывод: задача выглядит как **упаковка + рантайм-контракт**, не как
переписывание ядра. Ниже — что нужно сделать и что осталось решить.

## Что нужно сделать

### 1. Docker-образ демона

- Базовый образ с Python 3.12 (как в `pyproject.toml`), `uv` для
  установки зависимостей по `uv.lock` — тот же набор, что и host-
  инсталляция, без Tauri/GUI-частей.
- Внутрь образа поставить **только Docker CLI** (`docker-ce-cli` или
  аналог из пакетного менеджера базового образа) — не полный Docker
  Engine, демону не нужен свой daemon внутри, только клиент, который
  говорит на смонтированный host-сокет.
- Entrypoint — `packaging/run_daemon.py` (или его контейнерный аналог)
  в headless-режиме, без всего, что тянет desktop-обёртку.
- Опубликовать образ в CI, по аналогии с тем, как сейчас фризится
  macOS-бинарь (`freeze.sh`) — новый шаг публикации образа рядом с ним,
  тег на релиз.
- **Реестр — GHCR** (`ghcr.io/<owner>/odoo-sheller:<version>` и
  `:latest`), публикуется новым CI-воркфлоу на тег `v*`, рядом с
  `desktop-macos.yml`. Тот же хостинг/токен, что у самого репо, без
  второго аккаунта. Хранение и трафик для публичных образов сейчас
  бесплатны у GitHub. Не Docker Hub (лишний аккаунт/секреты без
  выгоды) и не только Dockerfile без публикации (это делает уровень 3
  резолвинга у мигратора не автоматическим — нужен был бы чекаут репо
  и локальная сборка именно в том случае, когда автоматизация нужнее
  всего).
- **Entrypoint сам подстраивает пользователя внутри контейнера** (не
  просто root, не переложено на вызывающего): старт от root, читает
  uid/gid владельца смонтированной `~/.odoo-sheller` и gid
  смонтированного `docker.sock` — это два разных gid, нужны оба, —
  создаёт под них пользователя (primary uid/gid от директории,
  supplementary group от сокета) и сбрасывает права (`gosu`/
  `su-exec`) перед запуском демона. Мигратор передаёt только `-v` и
  `-p`, ничего сверх. Причина: просто root на Linux сделает журналы
  root-only и нативный демон/desktop-приложение рядом их не прочитают
  — прямое противоречие требованию единой истории журналов (см. ниже).
  Сложность живёт один раз в образе, а не повторяется в каждом будущем
  вызывающем этого образа.

### 2. Рантайм-контракт (что мигратор обязан передать при старте)

- Смонтировать host `docker.sock` в контейнер демона:
  `-v /var/run/docker.sock:/var/run/docker.sock`.
- **Не требуется** подключать контейнер демона к docker network
  проекта — целевые Odoo-контейнеры достаются через `exec`/`ps` на
  сокет, не по сети (см. аудит выше).
- **Bind-mount на реальный host-путь `~/.odoo-sheller`**
  (`-v ~/.odoo-sheller:/root/.odoo-sheller` или эквивалент), **не**
  изолированный именованный Docker volume. Причина строже, чем просто
  «пережить перезапуск контейнера»: журналы контейнеризованного демона
  обязаны лежать в том же самом месте, что и у системно установленного
  Sheller (desktop-приложение, локальный бинарь) — единая история, не
  расколотая по трём разным хранилищам в зависимости от того, каким
  уровнем резолвинга он был поднят в этот раз. Если системного
  приложения ещё нет сейчас, а появится позже — оно должно увидеть уже
  накопленную историю по тому же пути.
- Порт 8765 — как обычно, наружу из контейнера на `127.0.0.1:8765`
  хоста (тот же принцип "bind только на localhost", что и сейчас, не
  публиковать шире).
- `ODOO_SHELLER_DOCKER` — не обязателен внутри контейнера (обычный
  `PATH` найдёт `docker` CLI), но имеет смысл явно задать для
  консистентности между режимами и для тестов.

### 3. Обновить README / Requirements

- В таблице Requirements добавить поддерживаемый контейнеризованный
  режим (сейчас там только "OS: macOS (daemon is not containerized)").
  Не убирать нативный macOS-путь — добавить второй, не заменить.

### 4. Тесты

- Интеграционный тест: демон в контейнере (socket-мост) → тестовый
  Odoo-контейнер рядом (через `docker compose`, отдельная сеть, но без
  network join с демоном — по пункту 2 не нужен) → полный цикл open
  session → exec → run_test → commit/rollback → close.
- Отдельно проверить `os_interrupt` (`docker exec <container> kill
  -INT <pid>`) именно из контейнеризованного клиента — механизм не
  должен зависеть от того, откуда вызван `docker`, но стоит
  подтвердить явным тестом, а не полагаться на аналогию.

## Что НЕ требует изменений

Protocol/framing, session state machine, bootstrap-скрипт, HTTP/WS API,
MCP-сервер — всё выше `transport.py` не зависит от того, где физически
запущен процесс демона. Меняется только упаковка и то, что монтируется
в рантайме.

## Открытые вопросы — решить в ходе разработки

- **Права на `docker.sock`.** Классическая головная боль
  Docker-outside-of-Docker: сокет обычно принадлежит группе `docker`
  на хосте, GID может отличаться от хоста к хосту. Варианты — рутовый
  процесс внутри контейнера, `--group-add $(stat -c '%g'
  /var/run/docker.sock)` при старте, или что-то ещё. Решить и
  задокументировать один способ.
- **Целевая ОС хоста.** Спека предполагает Linux-хост с Docker Engine
  (или Linux-контейнер Docker Desktop на Mac — там сокет тоже
  `/var/run/docker.sock` внутри VM, монтирование должно работать
  одинаково). Windows (`\\.\pipe\docker_engine`) — если не нужен на
  первом этапе, явно вынести из скоупа, не пытаться поддержать молча.
- **odoo.sh / SSH-режим внутри контейнера.** Сейчас не в скоупе
  Migrator (тот работает с локальными Docker-проектами), но если
  когда-нибудь понадобится — контейнеру нужен будет smtp/ssh-клиент и
  доступ к `~/.ssh` или переданным credentials. Не делать сейчас, но
  не проектировать так, чтобы это стало невозможным позже.
- ~~Persistent volume по умолчанию или нет.~~ Решено: bind-mount на
  `~/.odoo-sheller` хоста обязателен всегда, не опция — единая история
  журналов важнее, чем удобство одноразового ephemeral-запуска.
