# odoo-sheller в составе мигратора

Черновик. Не дизайн of record шеллера: где этот текст и
[docs/architecture.md](../docs/architecture.md) расходятся, побеждает
architecture. Сюда записан разговор 20 сентября 2026, чтобы не потерять
рамку. Какой из двух вариантов стыковки агента выбрать — ещё не решено.

Рабочий язык этого файла — русский. Код, API и канонические доки шеллера
остаются на английском.

---

## Зачем это рядом

Следующее приложение — механизм автоматической миграции целого проекта
(рабочее имя: ODO Framework). Типичный заказ: сотня кастомных модулей,
переход с Odoo 18 на 19.

Пайплайн примерно такой: модуль берётся по очереди → код мигрируется под
новый фреймворк → кладётся в addons контейнера 19 → живой Odoo проверяет
результат (upgrade, тесты, при необходимости правки) → следующий модуль.

Шеллер здесь не оркестратор и не «мигрируй модуль». Он — живой воркер:
persistent `odoo-bin shell` против реальной базы, exec, upgrade через ORM,
прогон тестов, журнал. Граф из ста модулей, перепись XML/Python, раскладка
файлов по addons, UI пайплайна — это мигратор.

Десктопное приложение odoo-sheller для этого контура **не обязательно**.
Встраивается демон и его HTTP/WebSocket API на `127.0.0.1:8765`. Десктоп
уже сам так устроен: окно — оболочка, UI — iframe на `/web`. Вкладка
мигратора может сделать то же самое; вкладка браузера на `/web` уже работает
рядом. Второго API под мигратор не делать.

```
мигратор (пайплайн, вкладки, граф модулей, чекбокс commit)
    │
    ├── HTTP/WS 127.0.0.1:8765     драйвер: open / exec / run_test / commit
    └── iframe /web                опционально смотреть, не печатать
              │
              ▼
         демон odoo-sheller
              ▼
         контейнер Odoo 19
```

Положить мигрированный аддон на addons path — Docker/volume, не шеллер.
После смены `.py` текущая сессия держит старый registry: нужен upgrade и
часто **новая сессия** (это уже сказано в `os_help('modules')`).

## Что у шеллера уже есть, без расширения протокола

- `POST /api/sessions` — открыть сессию, в ответе один раз `write_key`.
  Тело уже принимает `owner` и `allow_commit`.
- `POST .../exec` — в том числе
  `ir.module.module.update_list` / `button_immediate_install` /
  `button_immediate_upgrade`. Отдельного install-эндпоинта нет и не нужно.
- `GET /api/containers/{container}/tests?module=` и
  `POST .../run_test` — список классов и прогон **одного класса** за раз.
  «Прогнать модуль» = N последовательных вызовов. На одной сессии параллелить
  нельзя (`409 busy`).
- WebSocket `/ws/sessions` и `/ws/sessions/{id}`, `GET .../history`, журналы.
- Несколько сессий на одном демоне. Сессии умирают вместе с демоном.
- Одна команда на сессию, rollback по умолчанию, потолок exec по умолчанию
  5 минут (долгий upgrade может упереться).

MCP шеллера (`odoo_sheller/mcp.py`) — тонкий HTTP-клиент того же API.
`os_open_session` **специально** всегда шлёт `allow_commit: false`. Это
политика агента в чате, не запрет демона. Мигратор, если открывает сессии
сам, ходит в HTTP напрямую и ставит флаг из своего чекбокса.

## Кто здесь выдаёт разрешения

Admin key шеллера мигратору **не читать и не вставлять**.

Ключ существует, чтобы отличить клиентов на одном `127.0.0.1`: чужая вкладка
и MCP-агент не должны закрывать, забирать и грантить commit у сессии,
которую не открывали. Эндпоинт его не отдаёт, потому что страница `/web` —
обычный клиент той же API без логина.

В десктопном окне шеллера чтение `~/.odoo-sheller/admin.key` — удобство
наблюдателя чужих сессий. В миграторе другая роль: мигратор сессию
**открывает сам**, получает `write_key`, значит он владелец. Acting on a
session you own не требует admin key. Grant commit на своей сессии —
`POST /api/sessions/{id}/policy` с `X-OS-Session-Key`.

Чекбокс в миграторе («разрешить commit») мапится так:

- выкл → открыть с `allow_commit: false`. Пайплайн может ставить модуль,
  гонять тесты, откатывать. `POST .../commit` отказ, пока не разрешите.
- вкл → `allow_commit: true` сразу в `POST /api/sessions`, либо позже
  `POST .../policy` тем же ключом владельца.

Чтобы чекбокс что-то значил, пайплайнную сессию не открывать как
`owner.kind: human` на локальной базе: у человека там commit проходит
даже при флаге false (подтверждение считается UI). Владелец должен быть
`agent` с меткой вроде `migrator`.

Вкладка с `/web` внутри мигратора — наблюдатель, если не отдавать ей
write key. Смотреть пайплайн можно; печатать в сессию — нет. Не
подсовывать туда admin key.

Production по-прежнему `commit_forbidden`; чекбокс это не снимает.

## Как агент узнаёт, куда открывать сессию

Агент **не поймёт из инструкции**. Если в хосте висит шеллеровский
`os_open_session`, он откроет сессию сам, с `allow_commit: false`, мимо
чекбокса. Правило в тексте дешевле нарушить, чем звать мигратор. Путь
задаёт **набор инструментов**, не промпт.

Не называть это «админской сессией». Admin key ни при чём. Мигратор —
владелец: открыл, держит `write_key`.

Осторожно с handover (`POST /owner`, Grant access): право на commit
**не переезжает**. Новый владелец-агент всегда стартует с
`allow_commit: false`. Открыли с галкой и «отдали» агенту — галка
сбросится. Притачивание тем же ключом (`os_attach_session`) ключ не крутит
и владельца не меняет.

## Два варианта стыковки агента

Решение не принято. Записаны оба.

### Вариант 1 — мигратор открывает, агент притачивается тем же ключом

Мигратор: `POST /api/sessions` с `allow_commit` из чекбокса, забирает
`write_key`. Агенту отдают инструменты шеллера на работу в сессии
(`os_attach_session`, `os_exec`, `os_run_test`, `os_commit`, журнал) и
**не** отдают `os_open_session`.

Новая сессия на следующий модуль: агент не умеет открыть её в демоне.
Ему нужен инструмент мигратора («следующий модуль», «новая сессия под
этот аддон»). Мигратор открывает, отдаёт новый id и ключ.

Плюс: агент остаётся в знакомом ORM-цикле шеллера. Минус: граница
«кто открывает сессию» держится только отсутствием `os_open_session`;
ошибка в наборе tools возвращает модель в демон напрямую. Mигратор и
агент делят один write key — оба могут печатать.

### Вариант 2 — агент вообще не говорит с шеллером

Только MCP (или иной API) мигратора: взять модуль, прогнать тесты,
записать если галка стоит. Мигратор сам ходит в HTTP демона. Вопроса
«куда открывать сессию» нет. Шеллеровский MCP в этот хост не подключать.

Плюс: volume, upgrade, «нужна новая сессия после смены `.py`», порядок
ста модулей — знание мигратора, не модели. Минус: агент не видит живой
`env` напрямую; всё, что ему нужно из ORM, мигратор должен проксировать
или отдать как результат своих шагов.

Для пайплайна из 100 модулей вариант 2 обычно спокойнее. Для итерации
«агент чинит конкретный тест в уже поднятой сессии» удобнее вариант 1.
Имеет смысл не выбирать навсегда: пайплайн — 2, отладка одного модуля —
1, если набор tools разный в разных режимах.

## Примерный план, как шеллер входит в состав

Это порядок работ вокруг шеллера, не план всего мигратора. Пока без
обязательства менять протокол.

1. **Демон как зависимость, не как окно.** Мигратор сам спавнит
   `odoo-sheller` (или frozen binary) либо цепляется к уже живому `8765`,
   по тому же правилу, что десктоп: порт занят нами — attach; занят
   чужим — ошибка, порт не двигать. UI шеллера не копировать и не
   проксировать.
2. **HTTP-клиент в миграторе.** Open / probe / exec / run_test / commit /
   rollback / close / history. Write key только на стороне мигратора.
   Не ходить через `os_open_session`.
3. **Чекбокс commit** — единственное место, где решается запись в базу.
   Значение уходит в `allow_commit` при open или в `/policy`. Не в промпт
   агента и не в admin key.
4. **Вкладка «пайплайн»** — граф модулей, статус, логи оркестрации.
   Это UI мигратора.
5. **Вкладка «шеллер»** — iframe `http://127.0.0.1:8765/web` как
   наблюдатель той же сессии (WebSocket уже бродкастит). Без write key,
   без чтения `admin.key`. Если позже понадобится печатать из вкладки —
   отдать write key в фрейм, не admin key.
6. **Стыковка агента** — выбрать вариант 1, 2 или оба в разных режимах
   (см. выше). Пока не выбрано, не подключать шеллеровский MCP в хост
   мигратора «на всякий случай».
7. **Тесты модуля.** Мигратор: `list_tests` → по одному `run_test` на
   класс, таймаут с запасом, разбор stdout/stderr/журнала. Не ждать от
   шеллера эндпоинта «прогони весь модуль».
8. **Смена кода на диске.** После записи мигрированных файлов в addons —
   upgrade в сессии и/или новая сессия. Это шаг пайплайна мигратора.
9. **Не тащить в шеллер.** Перепись 18→19, зависимости ста модулей,
   сравнение поведения двух версий, UI пайплайна, политика «когда
   комитить». Если чего-то не хватает в воркере — сначала клиент
   мигратора, и только потом вопрос, менять ли демон.

  «Владение сессиями»). На target-контейнере `allow_commit: true`
  всегда, на source — `allow_commit: false` всегда, оба явно в теле
  `POST /api/sessions`. Подтверждено в коде (`session.py`): явный
  `allow_commit` в теле уважается для любого `owner.kind`, ограничение
  "агент не может с коммитом" — только внутри MCP-обёртки
  (`os_open_session`), которую мигратор не использует (ходит HTTP
  напрямую). Изменений в Sheller для этого не требуется.
- **Новое, из брейнштормa мигратора**: резолвинг демона на стороне
  мигратора предполагает три уровня — attach к системному → spawn
  локально установленного headless core → provision через Docker-
  образ того же core.
  - Уровень 2 проверен по коду/паковке этого репо: **уже готов
    архитектурно** — `packaging/odoo-sheller.spec` фризит демон
    отдельно от `odoo-sheller-app/` (macOS `.app`). Остался только
    вопрос дистрибуции: публикуется ли фриженный бинарь демона как
    отдельный скачиваемый артефакт (release asset), не только зашитый
    в инсталлятор `.app`.
  - Уровень 3 — **реально не поддержан и нужно решение**: README
    прямо фиксирует "OS: macOS (daemon is not containerized)" как
    требование, демону сейчас нужен Docker CLI на том же хосте, где
    он сам работает. Контейнеризованный режим демона (свой образ +
    `docker.sock` внутрь, Docker-outside-of-Docker) — новый заявленный
    режим работы, которого сейчас нет. Решить, стоит ли поддерживать.

Когда решение появится, этот черновик либо сжимается в английский кусок
канонических доков, либо остаётся локальной памяткой. Не раздувать
`docs/architecture.md` мигратором, пока шеллер не меняется.
