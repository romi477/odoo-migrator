## Обсуждение и решения (2026-09-20)

Черновик, накапливается по ходу брейнштормa. Не спека, не canonical design.

### Продукт

Дженерик, многоразовый инструмент: любой проект, любая пара версий Odoo
(не только 18→19). Правила миграции — не хардкод под одну пару версий,
часть продукта.

### Цикл миграции одного модуля

Два живых контейнера одновременно, оба через Sheller:

1. Старая версия — агент подключается сессией, читает, как модуль
   работает сейчас (`os_source`, exec, тесты).
2. Агент переписывает код модуля под новый фреймворк, руководствуясь
   правилами для этой пары версий.
3. Результат кладётся в директорию, подключённую к контейнеру новой
   версии (addons path).
4. Новая версия — агент открывает сессию, апгрейдит модуль, гоняет
   тесты и произвольный код, сверяет поведение со старой версией.
5. Если есть недочёты — правки, новая сессия, повтор цикла (пункты
   2–4), пока не станет зелёным.
6. Модуль считается готовым → пайплайн берёт следующий (см. автономность
   ниже).

### Правила миграции — гибрид

- Статичная база знаний по известным парам версий (Odoo релизится раз
  в год, пар конечное число) — аналог миграционных скриптов OpenUpgrade.
- Плюс агент сам исследует через `os_source`, когда база не покрывает
  случай (нестандартный код, кастомные паттерны).

### Владение сессиями — агент сам, не приложение

Пересмотрено после разговора про staleness сессии: приложение
открывать и передавать сессию n8n **не может** — после правки кода
текущая сессия держит старый registry (см. sheller-ru.md), а
agent-loop именно на правках и retry построен, значит ему нужна
свежая сессия почти на каждой итерации.

Решение: **агент (n8n AI Agent) сам владелец своих сессий**, сам зовёт
`POST /api/sessions` когда нужно, без похода к приложению за
разрешением:

- Старый (source) контейнер — сессии агента всегда `allow_commit:
  false`, явно в теле запроса, не настраивается.
- Новый (target) контейнер — сессии агента всегда `allow_commit:
  true`, явно в теле запроса. Не предосторожность, а механическое
  требование пайплайна: модуль 50 может зависеть от 1–49, без
  накопленных commit'ов в БД его не установить для проверки.

Отказ от чекбокса «разрешить commit» как per-батч ручки (была в
sheller-ru.md как ручка безопасности) — осознанный: единственный
барьер, который остаётся, зашит в самом Sheller и не снимается никак —
`target.stage == PRODUCTION` форсит `allow_commit = False`
безусловно (`session.py`, `CommitForbidden`, отдельная ветка от
обычного `CommitNotAllowed`). У мигратора нет пути, где
target-контейнер оказался бы `production` — миграция всегда локальная,
модули можно тянуть по SSH откуда угодно (в будущем, как odoo.sh
сейчас), но кладём их всегда в свой локальный target, никогда не
пишем во внешнюю систему.

**Подтверждено прямо в коде odoo-sheller (`session.py`), изменений в
Sheller не требуется**: `allow_commit=None` резолвится в `owner.kind
== "human"` (по умолчанию для агента — false), но явный `allow_commit`
в теле запроса уважается для любого `owner.kind`. Ограничение
"агент не может открыть с коммитом" существует только внутри MCP-
обёртки (`os_open_session` в `mcp.py`, хардкод `allow_commit: False`)
как политика чат-агента — мы туда не идём, зовём HTTP прямо.

Приложение больше не открывает/передаёт сессии — получает `session_id`
в result-callback-е от n8n, для live-iframe наблюдения, не для
управления.

### Роль n8n и Sheller — кто что делает

- **n8n = чистый исполнитель одной задачи**: «мигрировать модуль X».
  Workflow внутри — AI Agent node (LangChain), к которому привязаны
  tools = HTTP-запросы прямо на Sheller REST API (`/api/sessions`,
  `.../exec`, `.../run_test`, `.../commit` и т.д.). Никакого MCP
  шеллера в хосте мигратора — агент ходит в Sheller через HTTP, как
  описано в «Варианте 2» из sheller-ru.md.
- **Наше приложение = source of truth** для графа зависимостей модулей,
  очереди, батчей, чекпоинтов ревью и базы правил. n8n не хранит этого
  состояния — приложение дёргает n8n webhook-ом «мигрируй модуль X»,
  получает результат назад (webhook/поллинг), само решает, что дальше.
  (Рассматривался вариант «n8n — source of truth через Data Store» —
  отклонён: граф модулей, mouse-select батча, база правил — не то, для
  чего сделан data model n8n.)

### Автономность — конфигурируемые батчи

Юзер выделяет на графе модулей блок (от 1 до N модулей), жмёт
«migrate» → блок уходит в автономную работу (цикл выше по каждому
модулю без остановки) → по завершении блока — пауза → юзер идёт
смотреть живые контейнеры (обе версии) через UI, делает ревью → решает,
продолжать ли на следующий батч. Размер батча = 1 даёт ревью после
каждого модуля; больше — ревью раз в блок.

### UI — десктоп-приложение (как у sheller)

Окно-оболочка, тот же паттерн, что у sheller (окно — shell, UI — iframe).
Внутри:

- iframe с canvas n8n — сама логика workflow (граф нод, не граф
  модулей).
- iframe с sheller `/web` — наблюдение живой сессии (без write key,
  наблюдатель).
- Отдельная панель «прогресс пайплайна» — живой статус сотни модулей
  (очередь/в работе/готово/фейл), это не то же самое, что canvas n8n.
- Меню настроек.

### Граф зависимостей модулей

Не парсим `__manifest__.py` сами. Приложение при старте просит:
проект + версия-источник + версия-цель. Контейнер старой версии должен
быть уже запущен, либо поднимается с интерфейса. Дальше через Sheller
идёт сессия в живую ODA старой версии, граф модулей резолвится
средствами самого Odoo (он это умеет — install/dependency graph) и
возвращается в приложение как дерево.

В UI дерево редактируемое: можно вычеркнуть уже мигрированные модули,
перетаскивать/перегруппировывать узлы, чтобы разложить в
последовательный пайп (батчи для автономного прогона, см. выше).

### Критерий «модуль готов» — уровень сложности, настраиваемый

Задаётся с интерфейса, на модуль или на группу модулей.

- **Базовый уровень (обязателен всегда)**: модуль устанавливается,
  апгрейдится, автотесты (`run_test`) зелёные, в логе/stderr нет
  ошибок.
- **Повышенный уровень (опционально)**: плюс агент обязан дёргать все
  бэкенд-методы модуля напрямую (не только через тесты) — на случай,
  если модуль зовёт дженерик-метод фреймворка, который в новой версии
  переименован/убран, а тестами это не покрыто.
- В обоих уровнях агент обязан читать warnings в stdout/stderr
  (deprecated методы/поля новой версии) и реагировать на них, а не
  просто пропускать как "не ошибка".

### Retry внутри модуля

Цикл «правка → upgrade → test» внутри одного модуля (agent-loop в n8n
workflow) гоняется до зелёного либо до лимита попыток. Лимит —
настраиваемый параметр интерфейса (как уровень сложности), не
захардкожен. Упёрлись в лимит → workflow возвращает `failed` с логом
всех попыток → модуль red в дереве → батч останавливается на нём, ждёт
человека (не продолжает молча дальше).

### Выбор модели — per батч, не per агент-исполнитель

Меняется только LLM-модель/провайдер под капотом нашего n8n AI Agent
node (тот же tool-use цикл, Sheller как tools) — не замена всего
агента-исполнителя на внешний CLI-инструмент (Cursor/OpenCode/Claude
Code и т.п., у которых своя оркестрация). На батч можно поставить
дорогую сильную модель или дешёвую слабую — экономия на простых
модулях.

Реализация — не runtime-параметр в JSON payload (внутри одной ноды
неудобно динамически прыгать между провайдерами, у каждого свои
credentials/node type), а на уровне canvas:

- Общая agent-loop логика (читать старую версию → правки → тест →
  retry) — один shared sub-workflow (Execute Workflow node).
- На canvas — несколько тонких workflow-обёрток, каждая = конкретная
  модель/credentials + вызов общего sub-workflow (например
  `migrate-module-claude`, `migrate-module-deepseek`,
  `migrate-module-gpt`).
- Приложение на батч выбирает, какой webhook (какую обёртку) звать —
  выбор модели декларативный и виден на canvas, не спрятан в payload.

### Обратная связь человек↔агент по модулю

Третий канал общения приложение↔n8n (помимо «запусти модуль X» и
«результат готов»):

- **Заметки по модулю** — persistent knowledge, не про пару версий
  вообще (это Rules Store), а про конкретный модуль. Юзер пишет в
  любой момент, особенно когда модуль встал в `failed`: «сделай так,
  потому что так». При повторном запуске этого модуля заметка уходит
  в payload как доп. контекст агенту. Хранится в приложении (source of
  truth), не в n8n.
- **Агент сам может спросить человека** — tool `ask_human(question)` в
  тулсете AI Agent node. Вызов → workflow встаёт на паузу (n8n `Wait`
  node, resume через webhook), в UI у модуля новый статус
  `waiting_for_human` с текстом вопроса (отдельно от `failed` — это не
  упор в лимит попыток, это осознанная пауза). Человек отвечает в
  интерфейсе → приложение дёргает resume-webhook n8n с ответом →
  agent-loop продолжается.
- Батч не должен тихо считать `waiting_for_human` как «продолжаем
  дальше» — так же, как `failed`, это стопорит батч на этом модуле до
  реакции человека (иначе смысл вопроса теряется).

**Режим «Don't ask human»** (чекбокс, на батч или глобально) — на
случай, если человек отошёл и не хочет стопорить пайплайн на вопросах:

- `ask_human` не ставит workflow на паузу. Агент обязан сам принять
  best-effort решение (с явным указанием, что это допущение), и
  продолжить цикл.
- Вопрос + принятое допущение логируются в накопитель, не блокируют
  модуль. Модуль идёт обычным путём (pass/fail по критериям), но
  помечается флагом «есть допущения на ревью», даже если зелёный —
  отдельно от чисто чистого прохода.
- На чекпоинте конца батча накопленные вопросы+допущения показываются
  человеку вместе с обычным ревью. Правки уходят как заметки по модулю
  (механизм A выше) и запускают точечный повторный прогон именно этих
  модулей.

### Desktop shell

Tauri (не Electron — тяжеловесный), тот же паттерн, что у sheller.

### Окружение n8n (справка, по офиц. докам n8n)

- npm-установка n8n официально deprecated с версии 3.0 — доки сами
  говорят ставить через Docker Compose или one-line setup script
  (`curl -fsSL https://get.n8n.io | sh`).
- Docker Compose путь — официальный минимум 4GB RAM + 2 vCPU.
- В стандартном compose есть `sandbox-runner-1` — сендбокс для
  AI-generated code через Docker-in-Docker, ест больше ресурсов, чем
  обычный контейнер. У нас код агент не гоняет через n8n Code node —
  всё выполнение кода идёт через Sheller (см. выше), так что этот
  сендбокс, скорее всего, не нужен / можно не поднимать. Проверить при
  реализации.
- Итого локально на Mac: Docker для n8n + Docker для двух Odoo-
  контейнеров (старая/новая версия) + свой backend без Docker (venv).
  Не невесомо, но нормально для дев-машины.

### Порядок разработки

Сначала браузерное web-приложение (MVP, чтобы не отвлекаться на
десктоп-обёртку сразу), потом заворачивается в Tauri desktop shell
(см. выше).

### Свой backend — без контейнера

Backend приложения (Python + venv достаточно, жёстких зависимостей не
предполагается) не упаковывается в Docker — это инструмент, который
управляет чужими контейнерами (Odoo старой/новой версии), не сам себе
контейнер. Дистрибуция позже — через Tauri-бандл.

### Провижининг Docker-контейнеров проекта

Юзер на старте указывает путь к старому проекту и путь к новому
(целевому) проекту. В обоих уже подготовлен compose-файл (готовит
юзер/девопс, не генерируем автоматически). У приложения ручки:

- **up** — поднять контейнеры из compose, если не запущены;
- **attach** — присоединиться, если уже запущены (тот же принцип, что
  у sheller: порт занят нами — attach, занят чужим — ошибка, не
  трогаем);
- **restart / rebuild** — по необходимости.

Это детерминированная инфраструктурная работа (docker-compose
CLI/SDK), не агентская задача — делает backend приложения напрямую,
без LLM/MCP. Агент (n8n AI Agent) работает только через Sheller на
уровне Odoo, в Docker не лезет — граница между «приложение держит
инфраструктуру» и «агент мигрирует код» остаётся чистой.

### Резолвинг Sheller-демона

Три уровня, по убыванию приоритета, вместо простого «attach или
ошибка»:

1. **Attach к системному** — пробуем порт (8765 по умолчанию). Живой
   Sheller API на нём → цепляемся клиентом, lifecycle чужой, не
   трогаем (не убиваем при выходе мигратора). Покрывает «уже открыт
   десктоп sheller / кто-то уже поднял демон».
2. **Spawn локально установленного core** — порт свободен → ищем
   `odoo-sheller` бинарь/CLI в системе (headless-режим, без своего
   Tauri UI). Нашли → сами спавним подпроцессом, сами владеем
   lifecycle.
3. **Provision через Docker-образ** — ни порта, ни локального бинаря
   нет → тянем `odoo-sheller-core` образ, поднимаем сами, монтируем
   `docker.sock` внутрь (Docker-outside-of-Docker, чтобы демон внутри
   мог по-прежнему сам делать `docker exec` в целевые Odoo-
   контейнеры). Мигратор владеет lifecycle.

Ни один уровень не сработал → явная ошибка юзеру, не тихий фолбэк.

**Уточнение по уровню 3, после ревью спеки sheller-проекта
(`odoo-sheller/docs_/superpowers/specs/2026-09-20-containerized-daemon-design.md`)**:
образ на GHCR остаётся **private** (осознанное решение sheller-
проекта, обратимо только в одну сторону — public назад не откатить).
Значит уровень 3 у нас больше не полностью автоматический: на каждом
новом хосте перед `docker run` нужен `docker login ghcr.io` с токеном
`read:packages`. Private принят осознанно (2026-09-20) — на раннем
этапе доступ к приложению и так под контролем, кому нужно — выдаём
вручную, это не проблема сейчас. Открыт только технический вопрос:
(a) мигратор сам просит токен в настройках и делает `docker login` от
имени юзера при первом срабатывании уровня 3, или (b) документированный
ручной шаг на новой машине, не автоматизируем. Не блокер, решить при
реализации.

Также фиксировано контрактом sheller-проекта: имя контейнера
`odoo-sheller` и порт `8765` — жёстко зашиты (нужны для MCP-эскалации
через `docker exec -i odoo-sheller ...`). Значит на одном хосте не
может быть двух sheller-core контейнеров параллельно — это
согласуется с тем, как sheller и так устроен (один демон на хост,
много сессий внутри), но важно не пытаться параметризовать имя/порт
под будущий сценарий "несколько проектов на одной машине одновременно".

Владение сессиями (agent-owner, не читать `admin.key`) не зависит от
того, какой уровень сработал — это уже решено в sheller-ru.md.

**Проверено по репо `odoo-sheller` (README/architecture.md), не
гадаем больше:**

- Демон — обычный host-процесс, сам держит `docker exec -i <container>`
  как pipe в `odoo-bin shell`. В целевой контейнер ничего не ставится
  и не копируется (bootstrap течёт через stdin heredoc самого exec-
  канала) — контейнер готовить заранее не нужно ни для одного уровня.
- **Уровень 2 — уже архитектурно готов**: `packaging/odoo-sheller.spec`
  фризит демон отдельно от `odoo-sheller-app/` (macOS `.app`-обёртка).
  Остаётся вопрос дистрибуции (публикуется ли фриженный бинарь демона
  отдельно от инсталлятора десктоп-приложения), не архитектуры.
- **Уровень 3 — требует реального решения в sheller**, не просто
  паковки: README прямо фиксирует "OS: macOS (daemon is not
  containerized)" как требование. Демону сейчас нужен Docker CLI на
  том же хосте. Контейнеризованный режим (свой образ + `docker.sock`
  внутрь) технически похож на рабочий паттерн, но это новый заявленный
  режим, которого сейчас нет — решать в sheller-ru.md/architecture.md.

### Формат базы правил по версиям

Вариант A — просто файлы (markdown/yaml) в репо продукта, по одному на
пару версий (например `rules/17-to-18.md`), человекочитаемые,
версионируются git, ревьюятся как код/доки. Не БД, не UI-редактор —
это статичная, курируемая знаниевая база продукта.

(Заметки по конкретному модулю — другое: то живёт в БД приложения,
рядом с очередью/статусами, см. «Обратная связь человек↔агент по
модулю» выше.)

### Webhook-контракт приложение↔n8n

**Trigger (app → n8n webhook, POST)** — уже без предоткрытых сессий,
агент открывает их сам (см. «Владение сессиями» выше):

```json
{
  "job_id": "uuid",
```
