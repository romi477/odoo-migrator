Guide

The steps under the open migration, in menu order. For field-level detail and settings, see docs/ui-guide.md in the repo.

  1. Tree

    The dependency graph for this migration. Colour is the step (wave). A later wave cannot run until every module on earlier waves is passed or left out.

    • Build graph reads installed custom modules and depends from the source Odoo (via Sheller) and redraws the graph and steps.
    • Step buttons above the canvas select every module on one wave; optional help sits under the node card.
    • Node card (dashed panel under the step buttons): #rank/step, name, status, and Exclude or Include for the current selection. A whole step or multi-select shows both buttons. Exclude all and Include all apply to the whole migration.
    • Exclude / Include follow the graph: exclude hits the selection and everything downstream; include walks each module's depends chain upward. A lone leaf (nothing depends on it) is excluded on its own — parents stay in the plan.
    • Drag one node onto another to put them in the same batch group. Runs start on Pipeline, not here.
    • Answer appears on the card when status is waiting_for_human and the module is still in the plan.
    • Struck nodes show (out), dashed borders, and faded colour. The attention lamp opens Tree with ?focus= on the stalled node.

  2. Pipeline

    Where you queue work and watch the live stage. When a batch finishes, checkpoint review is on this screen too.

    • Selection — pick a Step (same waves as Tree), see its module list, Add to queue or Add all steps to queue. Duplicate steps are ignored.
    • Queue (FIFO) — pending modules in migration order (#rank/step on each row). Collapsed view shows the next module only; click the queue header (chevron) to expand or collapse the numbered list. Run / Stop stay separate. Run / Stop drive the pipe (you can add steps while running; Stop waits for the current module). Clear drops the list when the pipe is stopped and no module is still running. The active row pulses.
    • Live panel below — module name, status, stage, attempt. Empty reads “No module is running.” SSE updates without a reload.
    • When the batch hits checkpoint, a banner asks you to reload for review. Then Continue (disabled while failed or waiting jobs are unread), Override, Dismiss per stalled job, and Promote to append a finding to a rules file you choose.

  3. Sheller

    Odoo in observer mode: Sheller's /web iframe edge to edge. The frame has no write key.

    • Pick the live session inside Sheller's own UI. Do not append ?session= — Sheller ignores it.

  4. Result

    The migration scoreboard: progress for modules still in the plan, then one column per dependency wave.

    • Columns are L0, L1, … — the same waves as Tree. More than four waves paginate: four columns per page, dashes in the panel header (one dash per page; active is cyan).
    • Each card uses the step colour on the full outline. A filled corner badge marks passed (green check), waiting for you (warning, pause bars), or excluded (left out on Tree). Running, queued, or failed modules use a small inline badge instead.
    • Subtitle is parent depends, or excluded — skipped on Tree. Skipped modules stay in their wave with the name struck through.
    • SSE updates cards while this screen is open. With no graph yet, resolve on Tree first.

Flow

The pinned flow, drawn. Nothing on that screen is stored; the picture is computed from the file each time it is opened. The names below are the stock flow. An imported flow draws its own steps and is read the same way.

Two frames. Pipeline is the lap every module takes. On failure is the side lane, entered when any pipeline step fails — the dashed arrow is labelled any step fails, and it leaves the frame, not one block. Orange blocks are a model turn. Quiet blocks are the app itself, with no model. A dashed border and if … means the block is skipped unless an earlier step raised that flag. The cut rectangle stops the run and waits for you. Solid arrows are the order inside a frame. The orange dashed arrow retry leaves the side lane once, into lint, and the lap continues from there. How many laps are allowed is the retry limit on the migration.

Pipeline

  • understand reads the module on the source Odoo, through a live session on that container. It describes current behaviour, what the module overrides, and what will break on the target. It also builds the smallest set of records the module needs, proves that recipe works, and rolls it back. The recipe is the answer later steps replay.
  • port writes the ported module into the target project. Both sessions stay open, so it can check what the original does. It sees the version rules, the module source, and the understand answer.
  • lint does not touch a container. It checks that the new module's Python parses, its XML parses, and its manifest is a dict with name and depends. A problem fails the lap.
  • upgrade installs the module on the target container, or upgrades it if it is already installed, then commits. The source container is never committed.
  • tests runs the module's own test classes on the new container. No test classes is a success that raises no_tests, which is what opens the next two blocks. A failing test leaves the pipeline for the side lane.
  • probe if no_tests replays the understand recipe on both versions, calls the same methods, and reports every difference. A recipe that will not replay on the new version is a failure of its own.
  • write_test if no_tests turns that recipe into a real test in the ported module, asserting what the source version did, and runs the test before it finishes.
  • verdict judges the lap. At strictness strict it fails when probe left no answer. basic and enhanced do not add a check of their own.

On failure

The lane runs top to bottom. A block with a flag runs only when diagnose raised it, so a small fix and a rewrite are alternatives, not a sequence. Then the lap resumes at lint: understand and port are not repeated.

  • diagnose works out why the lap failed, from the log, the journal, the source, and a live session on the target container. It raises the flags that open the blocks under it: needs_human, reexamine_source, small_fix, start_over.
  • ask_human if needs_human parks the job. The question is the diagnosis. Both sessions close while it waits. You answer on Tree, and the same run continues. If the thread that was waiting is gone, the answer is kept and the job becomes unknown.
  • reprobe if reexamine_source goes back to the source version with the question the diagnosis raised.
  • patch if small_fix applies that fix on the target side. It has the previous diff and is told to change what is wrong and leave the rest.
  • rewrite if start_over writes the module again from the source version. It is not given the previous attempt.

The picture and nothing else. The tool calls a run made are the run log on Pipeline, which had them already; a second list under the diagram meant reading one job on two screens. Opening a tool-call line there fetches the command's whole record from Sheller's journal, which is what this list used to be the only way to reach.
