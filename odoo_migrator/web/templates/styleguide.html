Guide

Two parts. Menus says what each screen under the open migration is for. Cartridge language says what a flow file is made of: its keys, steps, tools, context and flags. Field-level detail and settings are in docs/ui-guide.md and docs/cartridge-reference.md in the repo.

button or screen step tool YAML key flag context item

1. Menus

The screens under the open migration, in menu order.

  1. Tree

    The dependency graph for this migration. Colour is the step (wave). A later wave cannot run until every module on earlier waves is passed or left out.

    • Build graph reads installed custom modules and depends from the source Odoo (via Sheller) and redraws the graph and steps.
    • Step buttons above the canvas select every module on one wave; optional help sits under the node card.
    • Node card (dashed panel under the step buttons): #rank/step, name, status, and Exclude or Include for the current selection. A whole step or multi-select shows both buttons. Exclude all and Include all apply to the whole migration.
    • Exclude / Include follow the graph: exclude hits the selection and everything downstream; include walks each module's depends chain upward. A lone leaf (nothing depends on it) is excluded on its own — parents stay in the plan.
    • Drag one node onto another to put them in the same batch group. Runs start on Runner, not here.
    • Answer appears on the card when status is waiting_for_human and the module is still in the plan.
    • Struck nodes show (out), dashed borders, and faded colour. The attention lamp opens Tree with ?focus= on the stalled node.

  2. Runner

    Where you queue work and watch the live stage. When a batch finishes, checkpoint review is on this screen too.

    • Selection — a chip for each step (same waves as Tree). Point at one to see its modules; press the one with the arrow to put every module of it in the queue, or press Add all for every step. A step opens once the steps it depends on are in the queue. Duplicate steps are ignored.
    • Queue (FIFO) — pending modules in migration order (#rank/step on each row). Collapsed view shows the next module only; click the queue header (chevron) to expand or collapse the numbered list. Run / Stop drive the pipe (you can add steps while running; Stop waits for the current module). Clear drops the list when the pipe is stopped and no module is still running. The active row pulses.
    • Live panel below — module name, status, stage, attempt. At rest the machine is drawn with empty slots. SSE updates without a reload.
    • When the batch hits checkpoint, a banner asks you to reload for review. Then Continue (disabled while failed or waiting jobs are unread), Continue anyway, Dismiss per stalled job, and Promote to append a finding to a rules file you choose.

  3. Flow

    The pinned flow, drawn. Nothing on that screen is stored; the picture is computed from the file each time it is opened. An imported flow draws its own steps and is read the same way. What the steps are called and do is in Cartridge language.

    • Two frames. Pipeline is the lap every module takes. On failure is the side lane, entered when any pipeline step fails — the dashed arrow is labelled any step fails and it leaves the frame, not one block.
    • Orange blocks are a model turn. Quiet blocks are the app itself, with no model.
    • A dashed border and if … means the block is skipped unless an earlier step raised that flag. The cut rectangle stops the run and waits for you.
    • Solid arrows are the order inside a frame. The orange dashed arrow retry leaves the side lane once, into lint, and the lap continues from there. How many laps are allowed is the retry limit on the migration.
    • The eye beside the Flow field on the migration card opens the file; Fork copies it into editable text and Save fork stores the copy as a new flow.

  4. Sheller

    Odoo in observer mode: Sheller's /web iframe edge to edge. The frame has no write key.

    • Pick the live session inside Sheller's own UI. Do not append ?session= — Sheller ignores it.

  5. Result

    The migration scoreboard: progress for modules still in the plan, then one column per dependency wave.

    • Columns are L0, L1, … — the same waves as Tree. More than four waves paginate: four columns per page, dashes in the panel header (one dash per page; active is cyan).
    • Each card uses the step colour on the full outline. A filled corner badge marks passed (green check), waiting for you (warning, pause bars), or excluded (left out on Tree). Running, queued, or failed modules use a small inline badge instead.
    • Subtitle is parent depends, or excluded — skipped on Tree. Skipped modules stay in their wave with the name struck through.
    • SSE updates cards while this screen is open. With no graph yet, build it on Tree first.

2. Cartridge language

A cartridge is a YAML file that says how one module is migrated: which steps run, in what order, what each may touch and what it is told. It is pinned per migration and recorded on every job. The stock one ships with the app as cartridges/stock.yaml. The vocabulary is closed: a file picks names from the lists below and never adds to them.

A key the loader does not know is ignored, not refused. A misspelt contexts: does nothing and raises no error, so after editing a file open it on Flow and check that the step shows what you wrote.

The file

cartridge: mine
version: "1.0.0"
schema: 1
model: {provider: anthropic, name: claude-sonnet-5-5}
pipeline:
  - step: agent
    id: port
    sessions: [source, target]
    tools: [exec, source, read_file, write_file]
    context: [rules, module_source]
    prompt: |
      Port the module to the target version.
  - step: lint
  - step: upgrade
  - step: tests
  - step: verdict
on_failure:
  pipeline: []
  retry:
    resume_at: lint

Top-level keys

cartridge
The flow's id. Identity is this plus version. Fork accepts letters, digits and . _ + -, 40 at most.
version
The flow's version. Quote it when it looks like a number: a bare 1.0 is a float, not a string.
schema
The file format. This build implements 1; any other is refused.
model
The model the flow was written for: provider (anthropic, openai, cursor or local) and name. A provider or name the app does not know is refused. See "Which model runs a step" below.
pipeline
The ordered list of steps of one lap.
on_failure
What happens when a step fails: pipeline, a list of steps (the side lane), and retry.resume_at, the id of a pipeline step the lap restarts from after the lane.

Step keys

A step is one entry of pipeline or of on_failure.pipeline.

step
Required. The kind: one of the step kinds below.
id
Required on an agent step, optional on the others. The step's name on Flow and the key its answer is stored under. Unique across the whole file. A step without one is named by its kind.
when
A flag name. The step runs only if that flag was raised earlier in the same lap; otherwise it is skipped, and the run log says why.
sessions
agent only. source, target or both: which containers the step may reach.
tools
agent only. Names from the tool list below. A tool that none of the step's sessions allows is refused.
context
agent only. Names from the context list below, rendered above the prompt in a fixed order whatever order you list them in.
raises
agent only. The flags the step may set. They become the fields of its report tool.
prompt
Required on an agent step, forbidden on the others.
model
agent only. provider and name for this step alone. Wins over everything else.
budget
agent only. tool_calls and tokens: ceilings for one run of the step, honoured only when lower than the app's own (60 calls, 400000 tokens).
fresh
Boolean. The module's directory on the target is emptied before the step runs. Only on an agent step whose tools include write_file.

Step kinds

The value of step. Everything but agent is the app itself: no model, no prompt, no tools, and only step, id and when as keys.

agent
One model turn-loop: the prompt, the tools and the context the step declares. It ends when the model calls report. Raises what its raises lists.
lint
No container. The module's Python parses, its XML parses, its manifest is a dict with name and depends. Raises lint_failed.
upgrade
Installs the module on the target container, or upgrades it if it is already installed, then commits. The source container is never committed.
tests
Runs the module's own Python tests with Odoo's runner, and its browser suite where the source ships one. Raises no_tests when the module declares no Python test classes and tests_failed when a test fails, a characterization test is missing or browser tests did not reach the target. A suite the target cannot run is a finding, never a pass.
clickbot
Odoo's own clickbot over the module's menus on the target, as admin with debug on, in a test transaction (Sheller 1.12.0 or later, Chromium in the container). A menu the port broke fails the lap; one that fails on the source too, menus it did not reach and a run that could not happen are findings.
smoke
No model, nothing written. On the target it makes a new record of each model the module declares fields on, evaluates each window action's domain, renders each report, compiles each asset bundle, and lists every button and every action a person runs from the Action menu. A break in the module's own code fails the step, unless the same break shows on the source: then it is a finding. Raises has_buttons when the module puts a button in a view.
verdict
Judges the lap against the migration's strictness. Reads behaviour_differs and button_broken.
ask_human
Parks the job and opens a checkpoint. The diagnosis in the last answer is the question. Both sessions close while it waits; you answer on Tree and the same run continues.

Steps of the stock flow

The names on Flow are the id of each step, or its kind when it has none.

Pipeline

understand
Reads the module on the source Odoo through a live session: current behaviour, what it overrides, what will break on the target. Builds the smallest set of records the module needs, proves that recipe works and rolls it back. Raises needs_tests when the module ships no tests.
characterize
when needs_tests. Writes a characterization test of the source's behaviour, on a branch of its own in the source project. The only write the source side ever gets.
port
Writes the ported module into the target project. Both sessions stay open, so it can check what the original does. Sees the version rules, the module source, the understand answer and any hand changes.
lint
The lint kind.
upgrade
The upgrade kind.
tests
The tests kind.
clickbot
The clickbot kind.
smoke
The smoke kind.
click
when has_buttons. Presses every button the module puts in a view, on a record it shows on, as a person would, and rolls back. A button that reaches outside the database is not pressed. One that breaks on the new version and works on the old one raises button_broken.
probe
when no_tests. Replays the understand recipe on both versions, calls the same methods and reports every difference. Raises behaviour_differs.
write_test
when no_tests. Turns that recipe into a real test in the ported module, asserting what the source did, and runs it before it finishes.
retest
when no_tests. The tests kind again, so the test just written is run.
verdict
The verdict kind. At strictness strict it also fails when probe left no answer.

On failure

The lane runs top to bottom. A step with a flag runs only when diagnose raised it, so a small fix and a rewrite are alternatives, not a sequence. Then the lap resumes at lint: understand and port are not repeated.

diagnose
Works out why the lap failed, from the log, the journal, the source and a live session on the target. Raises needs_human, reexamine_source, small_fix or start_over.
ask_human
when needs_human. The ask_human kind.
reprobe
when reexamine_source. Goes back to the source version with the question the diagnosis raised.
patch
when small_fix. Applies that fix on the target. It has the previous diff and is told to change what is wrong and leave the rest.
rewrite
when start_over. Writes the module again from the source version, without the previous attempt.

Tools

A step declares tool names; the catalog is code and a file can pick from it and never extend it. A tool is valid on a side only if both the tool and the step's sessions allow it, and every call carries side. report ends the step, is given to every agent step and is not listed in a file.

Sheller: the live Odoo shell

exec
Run Python in the session's Odoo shell, with env bound. Source or target.
source
Read code in the container: a file or directory by path, or the code a model method runs by model and method.
journal
What Odoo logged in the session.
history
The commands the session has run.
run_test
Run a module, a test class or one test method; answers with counts and what failed. params is Hoot's filter for a browser suite.
list_tests
The test classes a module declares on disk, each with a ready spec, and its browser test files.
click_module
Odoo's clickbot over the menus of one installed module, as admin with debug on, in a test transaction. Always the whole module, up to 15 minutes.
interrupt
Stop the command the session is running.
rollback
Discard what the session holds uncommitted.

Held by the app

test_result
The report of the last run_test. Target only.
reopen
Close the session and open a fresh one. Needed after a file changes, because the running process does not re-import it.

Files on the host disk

Always inside the configured project roots; a path that escapes them is refused, not clamped.

read_file
Read a file of the project, by container path or relative to the project root. Source or target.
write_file
Write a file in the module's directory on the target. Target only.
write_source_test
Create a file under tests/ of the module on the source, only for a module that had no test when the step began, on a branch of its own. Source only.

Context items

What is rendered above a step's prompt, each under a heading with its name. You pick from this list and never write an expression. Every agent step also gets the standing prompt, the shell notes from the daemon and a "This run" block; none of that is set in the file.

rules
The rules stack for this migration: the shared rules, then one file per version from the source's next to the target's. They describe what the target changes.
project_notes
AGENTS.md, CLAUDE.md and READMEs of the source project, of each addons directory of the plan and of the module itself; clipped.
module_source
The module's text files as they are on the source, code first; clipped.
prior_answers
The answers earlier agent steps of this job gave, by step id.
previous_diff
The module now, against the module as the job found it.
hand_changes
What a person committed in the module's directory on the target since the app's last commit there.
last_failure
The output of the step that failed: test report, traceback, lint findings.
test_guide
What to pin, what to assert on, how to write and name a test.
buttons
The buttons smoke found in the module's views, one line each: model, method or action, label, when it is hidden, its confirmation, the view.

Flags

A flag is a name one step raises and another step's when reads. Nothing is parsed out of prose: an agent step raises a flag by setting it in report. Flags are collected per lap and start empty on each. small_fix and start_over cannot be raised in one report: they ask for different repairs.

no_tests
Raised by tests: the module declares no Python test classes. Browser tests do not count.
tests_failed
Raised by tests (and by clickbot for a menu the port broke).
lint_failed
Raised by lint.
has_buttons
Raised by smoke: the module puts a button in a view or defines an action a person runs.
behaviour_differs
Read by verdict: the lap fails at every strictness. An agent step raises it (probe does).
button_broken
Read by verdict: the lap fails at every strictness. click raises it.
needs_tests
Declared by the stock flow. understand raises it, characterize reads it.
needs_human
Declared by the stock flow. diagnose raises it, ask_human reads it. A lane step that lists it and raises none of its flags has decided nothing: the app raises it for the step.
reexamine_source
Declared by the stock flow. diagnose raises it, reprobe reads it.
small_fix
Declared by the stock flow. diagnose raises it, patch reads it.
start_over
Declared by the stock flow. diagnose raises it, rewrite reads it.

Which model runs a step

The first that applies: the step's own model; the migration card's provider and model pair; the card's model alone, under the cartridge's provider; the cartridge's model. Prompts are tuned against a model, so the file names the one it was written for, and a card can still replace it.

The lap

  1. The steps of pipeline run in order. A step whose when flag is not in the lap's flags is skipped.
  2. A step that fails runs the lane: each step of on_failure.pipeline in order, with its when.
  3. The lap restarts from the earlier of resume_at and the step that failed, with the flags cleared. The retry limit on the migration card bounds the laps, and a retry that would repeat the failure it just had stops.
